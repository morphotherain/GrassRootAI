# 数据与对象模型评估

> **目的**：说明当前 dyn 表、`ContainerID` / `OwnerID`、运行时实体与 Task 交互的**实际语义**，评估合理性，并给出**不推翻存档**的演进建议。  
> 模块归属：[[模块划分]] · Inventory / WorldModel / Data

---

## 1. 总评（结论先行）

| 维度 | 评价 |
|------|------|
| **大方向** | ✅ 合理 — 单表 `dynGameObjects` + 容器 indirection，贴近 EVE「一切皆 itemID」思路 |
| **MVP 可用性** | ✅ 能跑 — 船、货、装备槽、采矿、精炼、转移已贯通 |
| **语义清晰度** | ⚠️ 偏弱 — `OwnerID`、`ContainerID`、Component.`owner` .overload 多种含义 |
| **可扩展性** | ⚠️ 中等 — 虫洞/军团机库/任务实例/多角色所有权需补 **LocationKind** 或等价概念 |
| **运行时 vs 持久化** | ⚠️ 有缝 — 太阳系加载、是否在 space、`store()` 推导 SolarSystemID 规则需文档化 |

**一句话**：底层模型是 **EVE 式资产表的 MVP 简化版**，不是设计错了，而是 **两个 ID 字段承担了 EVE 里「location + owner + flag」多种语义**，缺少显式类型与不变量文档，导致你和 AI 都觉得「抽象」。

---

## 2. 当前数据层结构

### 2.1 表与职责

```text
┌─────────────────────────────────────────────────────────────┐
│  Static（EVEdata.sqlite 主库）                               │
│  invTypes, invGroups, dogma*, map*, industry*, …            │
└─────────────────────────────────────────────────────────────┘
                              │
                    ATTACH AS dyn（.save）
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  dynGameObjects     — 所有「物」：船、装备、矿石、飞行员胶囊…  │
│  dynContainers      — (hostObjectID, containerType) → bagID   │
│  dynObjectAttributes — 实例属性（quantity, damage…）          │
│  dynPilotsSkill / dynSkillQueue / dynMarketOrder / …         │
└─────────────────────────────────────────────────────────────┘
```

| 表 | 角色 | EVE 近似 |
|----|------|----------|
| `dynGameObjects` | 全局 object 行：类型、位姿、三列「关系」 | `entity` / item 行 |
| `dynContainers` | 宿主上的「Named bag」ID | cargo hold、hangar、slot bag |
| `dynObjectAttributes` | 实例属性 | dogma 实例属性 |

这是 **合理** 的：EVE 也是「item 有 location + owner」，你们用 Container 链 + SolarSystemID 表达 location 的 MVP 版。

### 2.2 `dynGameObject` 一行字段

```cpp
objectID, typeID, x,y,z, SolarSystemID, OwnerID, ContainerID, qw,qx,qy,qz
```

| 字段 | 设计意图 | 实际多种读法 |
|------|----------|--------------|
| **SolarSystemID** | 物「属于」哪个太阳系（空间上下文） | ① 在空间中的物体 ② 在货舱里的物体由 `store()` **向上推导** 写回 |
| **OwnerID** | 资产归属 | ① Pilot 行：`OwnerID = PilotID` ② 物品：角色 ID ③ `createObject` 时填 pilotId ④ 常填 `0` |
| **ContainerID** | 所在容器 bag | ① `0` = 不在任何 bag（在空间或根） ② 非 0 = 在 `dynContainers.containerID` 某 bag 内 |

## 3. 容器模型（两层，容易晕，其实是对的）

```text
Ship (objectID=100)
  └─ dynContainers: (100, CONTAINER_TYPE_CARGO) → containerID=501
  └─ dynContainers: (100, CONTAINER_TYPE_HIGH_SLOT) → containerID=502
       │
       └─ dynGameObjects: 矿石 objectID=200, ContainerID=501
       └─ dynGameObjects: 激光 objectID=201, ContainerID=502
```

| 概念 | 存哪 | 含义 |
|------|------|------|
| **Bag** | `dynContainers.containerID` | 抽象容器 ID，不是 world 里的一个 mesh |
| **Membership** | `dynGameObjects.ContainerID` | 物品在哪个 bag 里 |
| **Bag 类型** | `dynContainers.containerType` | 货舱 / 高槽 / 中槽 / …（见 `StorageMacro.h`） |

**评价**：✅ 与 EVE「同一 ship 多个 hangar flag」同类；用 `containerType` 区分槽位 **合理**。

**问题**：`BaseComponent.containerID` 与 `StorageComponent.containerID`（bag 自身 ID）同名 — 物品侧叫 **parentContainerID** 更清晰（文档/将来 rename，非必须立刻改表）。

## 4. OwnerID — 过载分析（你觉得抽象的核心）

### 4.1 当前代码里的几种语义

| 场景 | OwnerID 值 | 代码位置 |
|------|------------|----------|
| Pilot 胶囊 object | `= PilotID`（角色 ID） | `InitPilots`、`Pilot(_objectID, _PilotID)` |
| 查飞行员 object | `WHERE OwnerID=? AND typeID=164` | `getPilotObjectIDByPilotID` |
| 精炼产出物 | `= pilotId` | `RefiningSystemHandler` → `createObject` |
| 空间天体 / 无主物品 | `0` | 常见默认值 |
| SkillComponent | `ownerID` 字段 = pilotId | 与 Base 的 OwnerID 同源 |

### 4.2 与 EVE 对照

EVE  roughly 分离：

- **owner**（character / corp / alliance）
- **location**（hangar, cargo, solar system, …）
- **flag**（具体哪个 bag）

你们把 **owner 角色** 和 **Pilot 行自引用** 都塞进 `OwnerID`，且 **location 主要靠 ContainerID + 推导 SolarSystemID**。

**评价**：

- MVP 阶段 ⚠️ **可接受但必文档化**
- 长期 ⚠️ 军团机库、合同交付、NPC 掉落归属会不够

### 4.3 命名冲突（比字段本身更坑）

| 符号 | 实际含义 |
|------|----------|
| `Component::owner` | 指向宿主 `GameObject*`（ECS 常见） |
| `BaseComponent::ownerID` | 角色/资产归属 ID |
| `Pilot::PilotID` | 角色 ID（与 capsule 的 OwnerID 应对齐） |

`SolarSystemMgr::getOwnerIdById` 里曾写 `base->owner != 0`（指针与 ID 混用）— 属于 **语义混淆的直接 bug 风险**。

**建议（文档层，零回归）**：

| 现名 | 文档中称呼 |
|------|------------|
| `OwnerID` | **AssetOwnerID** 或 **CharacterID**（当指玩家时） |
| `PilotID` | 与 capsule 的 OwnerID 保持一致 |
| `Component::owner` | 改称 **hostObject**（将来 rename） |

## 5. ContainerID + SolarSystemID 联动 — `store()` 规则

`BaseComponent::store()` 核心逻辑：

```text
从当前 object 的 containerID 出发，沿 dynContainers 向上找 host object，
直到 containerID=0，用链顶对象的 SolarSystemID 写回当前行的 SolarSystemID。
```

**含义**：货舱里的矿石 **不单独「在空间」**，但 **SolarSystemID 跟随宿主船所在星系** — 合理。

**边界情况（需心里有数）**：

| 情况 | 行为 |
|------|------|
| 物品在货舱 | ContainerID→bag→ship；SolarSystemID 跟船 |
| 物品在装配槽 | 同上，跟船 |
| 物品在空间站机库 | 若 host 是 Station 且 Station 有 SolarSystemID — OK；**机库未建模时易糊** |
| 物品 ContainerID=0 | 视为空间根；SolarSystemID 即自身所在星系 |
| Pilot 找 currentShip | 用 Pilot 的 containerID → `getObjectIDByContainerID` → ship | 依赖 **Pilot 行的 ContainerID 指向 pilot storage bag** |

**评价**：✅ 推导规则是 coherent 的；❌ **规则只活在代码里**，没有写在 `Document/`，所以新人/AI 不敢改。

## 6. 运行时对象模型

### 6.1 加载路径

```text
Save ATTACH dyn
  → SolarSystemMgr::Init → loadSolarSystem(solarSystemID)
  → dynGameObjects WHERE SolarSystemID = ?
  → ObjectFactory + EntityComponentAssembler
  → p_mapObject[objectID] = GameObject
  → 若有 SpaceTransformComponent → space_objects（出现在空间）
```

**注意**：查询 **未** 过滤 `ContainerID = 0`。在舱物品也会进 `p_mapObject`，但通常 **无 SpaceTransform**，不会进 `space_objects` — 靠 Component 组合区分，**implicit 而非 explicit**。

**评价**：MVP ⚠️ 可行；扩展 Instance/WH 时建议显式 **LocationKind** 或加载过滤器。

### 6.2 EntityArchetype + Component 袋

| Archetype | 主要 Component | Domain |
|-----------|----------------|--------|
| Ship | Base, Attributes, Equipments, Slots×4, Cargo, Locking, Physics, SpaceTransform | 多域聚合 |
| Pilot | Base, Attributes, Skill | Character |
| Equipment | Base, Attributes, Equipment(+Weapon/Miner) | Fitting + Combat |
| Asteroid | Base, Attributes | Harvesting target |

**评价**：✅ Phase 7 Assembler 方向对 — **类型 = 组件配方**，比在每个子类重复 `AddComponent` 清晰。

**问题**：Ship 是 **多 Domain 的聚合根**（正常），但业务逻辑勿继续堆进 `Ship.cpp`；应下沉到 Component / System。

### 6.3 交互路径（Task）

```text
UI / Scene / 内部 Component
  → TaskMgr::addTask
  → SolarSystemMgr::handleTask
       ├─ targetSystem=SOLAR_SYSTEM → handlerType → Create/Transfer/Destroy
       └─ taskType → Entity dispatchTask → Component::handleTask / entityTaskHandlers
```

**评价**：✅ **Command 总线 + 双路由**（handlerType vs taskType）对 MVP 清晰；Phase 3 typed 化后更稳。

**Inventory 相关 Command**：

| Command | 效果 |
|---------|------|
| `transferObject` | 只改 `dynGameObjects.ContainerID` |
| `createObject` | INSERT 新行 + 可选 attributes |
| `destroyObject` | 删 object + 运行时 erase |
| `cargoStorage` / `addObject` | 组件内协议，采矿/堆叠 |

**评价**：✅ transfer/create 走 SolarSystem Handler 统一入口 — **合理**；与 EVE「资产操作走服务端一条链」同类。

## 7. 与 EVE 体量的差距（将来会疼的点）

| EVE 概念 | 你们现状 | 风险 |
|----------|----------|------|
| **location flag**（Cargo/Hangar/Jettison/Solarsystem…） | 仅 ContainerID + 是否在 space | 机库、递送、抛货、WH 隔离 |
| **owner type**（char/corp/alliance） | 仅 int OwnerID | 军团资产、Sov 建筑 |
| **singleton vs stack** | quantity 在 attributes | 船只能 1 条等规则需上层保证 |
| **instance 物品** | 无 | Mission/WH 实例与持久化存档分离 |
| **Station hangar** | Station 有组件，机库 bag 规则未显式 | 站内容器 Owner 易乱 |

这些 **不要求 MVP 全做**，但模块文档里应预留 **Inventory/Location** 子域，避免继续往两个 int 上堆语义。

## 8. 合理性分项打分

| 项 | 分 | 说明 |
|----|-----|------|
| 单表 dynGameObjects | 8/10 | EVE 同源思路，适合 SQLite MVP |
| dynContainers 二级结构 | 8/10 | 多 bag 清晰 |
| OwnerID 语义 | 4/10 | 过载，缺 ownerType |
| ContainerID 语义 | 6/10 | 结构 OK，命名与「bag ID / 父容器」易混 |
| SolarSystemID 推导 | 7/10 | 规则合理但未文档化（本文补） |
| 运行时加载 | 6/10 | 靠 SpaceTransform 隐式区分 space/inventory |
| Task 交互 | 8/10 | 边界清楚，typed 化后继续加强 |
| 静态/动态分离 | 7/10 | ATTACH dyn 好；DataSheet manager 仍散 |

2. **术语表**：AssetOwnerID、ParentContainerID、BagID、PilotID  
3. **注释/markers**：`// Invariant: Pilot capsule OwnerID == PilotID`

### 9.2 短期（可选 PR）

| 改动 | 收益 |
|------|------|
| `enum class LocationKind { Space, Container, StationHangar, … }` **仅存内存**，serialize 仍写 ContainerID | AI 有显式类型 |

| 改动 | 触发条件 |
|------|----------|
| `OwnerType` + `OwnerID` 或 corpId 列 | 军团/机库 |

**原则**：**additive schema**（新列可 NULL），不拆 `dynGameObjects` 主表。

## 10. 数据不变量（建议团队共识）

1. **每个 `dynContainers.containerID` 唯一对应一个 (hostObjectID, containerType)。**  
2. **若 `dynGameObjects.ContainerID != 0`，则该 object 不应出现在 `space_objects`（无 SpaceTransform 或显式 LocationKind=Container）。**  
3. **Pilot 胶囊行**：`OwnerID == PilotID`；`PilotID` 与 `SkillComponent.ownerID` 一致。  
4. **在船货舱/槽位内的物品**：`store()` 后 `SolarSystemID` 等于宿主链顶 object 的 `SolarSystemID`。  
5. **transferObject**：只改 ContainerID，不直接改 typeID/attributes（除非业务明确 consume）。  
6. **createObject**：必须填 typeID；ContainerID=0 表示先进空间或后续再 transfer。  
7. **Component::owner** 是 GameObject 指针，**never** 与 `BaseComponent::ownerID` 比较。

## 11. 物体交互 — 典型链路（帮助建立直觉）

### 11.1 右键「卸下装备」

```text
UIRButtonMenu → refreshEquipment Task + transferObject Task(目标=货舱 containerID)
  → TransferObjectHandler → updateContainerIDByObjectID
  → Equipments Refresh → Storage Refresh
```

### 11.2 采矿入仓

```text
MinerEquipments → cargoStorage RequestObject Task
  → StorageComponent → addObject Task → Asteroid
  → createObject Task（无现成堆叠）或 add 到已有 stack
  → cargoStorage Refresh
```

### 11.3 飞行员登船

```text
Pilot.containerID → dynContainers → ship 上 PilotStorage 的 bag
  → getObjectIDByContainerID → currentShip
```

**评价**：链长但 **每步 Domain 可辨**；Inventory + Harvesting + Fitting 交界 — 正是 Task 总线适合的场景。
