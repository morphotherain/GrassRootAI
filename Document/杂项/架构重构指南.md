# 架构重构指南

> **读者**：未来的你、协作者、以及在本仓库写代码的 AI。
>
> **目的**：说明「我们已经改了什么、为什么这么改、新代码该怎么写」。任务清单见 [[架构重构TodoList]]；本页讲**用意与约定**，不重复 checkbox。

---

## 1. 总原则

### 1.1 我们在解决什么问题

GrassRootAI 早期是 **God Object + 跨层 include + 复制粘贴** 堆出来的：

- `GameApp` / `SolarSystem` / 胖 UI 窗口 orchestrate 一切
- Task、渲染、DB、模拟边界模糊
- 同一组件被 `AddComponent` 和 `m_pXxx` 双轨引用
- 每帧无条件写 SQLite

重构**不是**换成 EnTT 纯 ECS，而是 **ECS-lite + 模块边界**：在保留 `GameObject` 子类、`shared_ptr`、现有存档格式的前提下，让职责可预测、改动可局部验证。

### 1.2 执行原则（写代码时请遵守）

| 原则 | 含义 |
|------|------|
| **一事一 PR** | 一次只做一个主题（如「Task 去 D3D」），不顺手大改 |
| **行为不变优先** | 架构搬迁时先保持游戏规则一致，优化语义另开 PR |
| **新界面用 UIF，旧界面碰到了再拆** | 不要「一次性重构全部 UI」 |
| **新实体改 Factory + Assembler** | 不要在每个子类 `Init` 里重复 `AddComponent` |
| **模拟层改动 → Rebuild All** | 见下文「编译陷阱」 |
| **UI 只发 Task** | 新功能禁止 `SolarSystemMgr::getInstance().xxx = ...` 直改模拟状态 |

### 1.3 为什么不 full ECS

| 因素 | 说明 |
|------|------|
| 现有实体是 **有类型的对象** | `Ship` 有跃迁状态机、`Pilot` 绑 `currentShip`，不是纯 ID |
| 持久化绑在 Component 上 | `BaseComponent::store()`、进站 `setContainerID` 等已贯通存档 |
| 无自动化测试 | 大爆炸重写回归成本极高 |
| 收益曲线 | 当前痛点用 Archetype + System + 脏标记即可缓解大部分 |

**方向**：继续向 ECS **靠拢**（System 编排、组件袋、统一 Task 入口），但不推翻 OOP Entity。详见 [[EntityComponent模型#与 ECS 的距离]]。

## 2. 模块地图（改完后的边界）

```
┌─────────────────────────────────────────────────────────┐
│  GameApp          场景 FSM、EnterGame / ReturnToMenu    │
│  SceneTransitionService   场景跳转条件（从 GameApp 抽出）│
└───────────────────────────┬─────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────┐
│  SaveGameManager    ATTACH/DETACH dyn、槽位 CRUD          │
│  SolarSystemMgr     太阳系集合、全局 Task 分发入口        │
│  TaskMgr            任务队列 + SystemType 路由            │
└───────────────────────────┬─────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
  ObjectFactory      EntityUpdateSystem    SectorSpatialSystem
  + Assembler        （实体 Update 遍历）   （sector 空间）
        │
        ▼
  GameObject 子类 + Component 袋
        │
        ▼
  IGameObjectRepository（BaseComponent 试点）
```

| 层 | 目录/类型 | 职责 | 不应依赖 |
|----|-----------|------|----------|
| **表现** | `include/UIF/` | 主菜单、存档 UI、JSON 布局 | `SolarSystemMgr` |
| **旧 UI** | `include/UI/` | 游戏内窗口（总览、仓库…） | 理想情况下只发 Task（Phase 4 未全做） |
| **场景** | `include/Scene/` | 渲染循环、挂 UI | 尽量少直接改 Mgr 内部状态 |
| **模拟** | `Object/`、`Component/`、`System/` | 实体、组件、轻量 System | D3D 渲染细节 |
| **Task** | `Task/`、`TaskHandler/` | 命令分发 | D3D（Phase 1 已去掉） |
| **数据** | `Database/`、`SaveGameManager` | 静态表 + dyn 存档 | — |

## 3. 已完成的重构：改了什么、为什么

### Phase A/C — 存档与主菜单闭环

**问题**：`SaveGameManager` 能写库，但无法「新建 → 玩 → 回主菜单 → 再读档」。

**做法**：

- `GameApp::EnterGameFromSlot` / `ReturnToMainMenu` 状态机
- 回主菜单时 **detach dyn + Shutdown Mgr**（避免串档、泄漏 handler）
- Phase C 用 UIF + `UINavigationStack` 做存读删

**写代码时**：进游戏走 `EnterGameFromSlot`；回主菜单走 `ReturnToMainMenu`；不要绕过 `SaveGameManager` 直接 ATTACH。

---

### Phase B — UIF 新 UI 框架

**问题**：旧 `UIBase` 难扩展、与 D3D 强耦合、布局写死在 C++。

**做法**：节点树 + `*.ui.json` + `UIRenderContext::DrawUIQuad`；MainScene 专用。

**写代码时**：

- **主菜单 / 存档相关** → 用 UIF，改 JSON，见 [[UIF框架设计]]
- **SpaceScene 内窗口** → 仍用旧 UI，除非主动做 Phase 4 某项

---

### Phase 1 — 依赖清理

**问题**：`Task.h` include D3D；Handler 构造器 `unique_ptr(this)` 自注册；vcxproj 把 `.h` 当 `.cpp` 编译。

**做法**：Task 只引 logger；Handler 由 `HandlerFactory` 显式 `registerHandler`；清理无用 include。

**写代码时**：Task / Handler 头文件 **不要** include `d3dUtil.h` / `D3DManager.h`。

---

### Phase 2 — 边界抽取

**问题**：`GameApp::UpdateScene` 堆满 magic number 和星门切换逻辑；`SolarSystem::addGameObject` 巨大 switch。

**做法**：

| 抽取 | 文件 | 用意 |
|------|------|------|
| 场景 ID | `SceneId.h` | 消灭 1/2/3/4 magic number |
| 跳转规则 | `SceneTransitionService` | GameApp 只 `SwitchToSceneId` |
| 跨系加载 | `SolarSystemMgr::switchToSolarSystem` | 星门场景不再散落改多个 Mgr 字段 |
| 实体创建 | `ObjectFactory` | category/group → 具体类型，一处维护 |
| 静态物 SQL | `mapDenormalizeManager` | `SolarSystem.cpp` 无 raw SQL |

**写代码时**：

- 新场景类型 → 改 `SceneId` + `SceneTransitionService` + `GameApp` 注册
- 新实体 category/group → 改 `ObjectFactory` + `EntityComponentAssembler`，**不要**在 `SolarSystem::addGameObject` 加 switch

---

### Phase 7 — Entity/Component（核心，详见 [[EntityComponent模型]]）

#### 7.1 Archetype + Assembler

**问题**：每种 Entity 在 `Init()` 里各自 `make_shared` + `AddComponent`，和 Factory 分裂。

**用意**：**组件清单 = 数据**，集中在 `EntityComponentAssembler`；子类 `Init()` 只做业务（绑名、注册 Task）。

#### 7.2 去掉双轨指针

**问题**：`Ship` 既有 `components` 又有 `m_pBase` / `m_pPhysics`，改一处易漏一处。

**用意**：**唯一访问路径** `GetComponent<T>()`；依赖用 `ResolveDependencies` 注入。

#### 7.3 组件袋 O(1)

**问题**：`GetComponent` 线性扫描 + `dynamic_cast`。

**用意**：`componentByType` 按 `type_index` 注册；热路径 O(1)，基类查询仍 fallback。

#### 7.4 依赖注入

**问题**：曾用 `hash_code` 比对类型；`InjectDependency` 满屏 cast。

**用意**：`ResolveDependencies` 用 `std::type_index`；组件可用 `ComponentDependencyBinder::BindShared`（见 `PhysicsComponent`、`LockingComponent`）。

#### 7.5 System 层

**问题**：`SolarSystem::Update` 同时管实体 tick、sector 网格、过期清理。

**用意**：

- `EntityUpdateSystem` — 清理 expired、`GameObject::Update`
- `SectorSpatialSystem` — sector 网格与 `currentSector`
- `SolarSystem::Update` **只编排 System 列表**

`Ship::Update` 仍保留 **接近/跃迁状态机**（实体特有逻辑，合理）。

#### 7.6 持久化脏标记

**问题**：`BaseComponent::Update` 每 tick `store()`，SQLite 写放大。

**用意**：

- `needStore` + 60 tick 节流
- `setContainerID` / `setSolarSystemID` **立即落库**（玩法关键）
- `SolarSystemMgr::Shutdown` **全量 flush**

**写代码时**：改 Base 字段用 setter 或 `MarkDirty()`；不要在新 Component 里每帧 `store()`。

#### 7.7 Task 统一 dispatch

**问题**：四个 Entity 各 copy 一份 `handleTask` + 内联 `unordered_map taskHandlers`。

**用意**：

```
handleTask → dispatchTask → DispatchEntityTask(entityTaskHandlers)
```

- Handler map 在 **`GameObject` 基类**，`unique_ptr` 堆分配
- 子类 override **`registerEntityTaskHandlers`** 注册 taskType
- 全局 create/transfer/destroy 仍在 **TaskMgr / SolarSystemMgr**

**写代码时**：Entity 上新 taskType → 在对应类的 `registerEntityTaskHandlers` 加一项；不要新建第二套路由。

#### 7.8 DB 边界试点

**问题**：`BaseComponent` 直接 include `dynGameObjectsManager`。

**用意**：`IGameObjectRepository` + `GetGameObjectRepository()`；Sim 层可换实现、Component 易测。

**写代码时**：新 Component 若需 dyn 读写，优先走 Repository 接口（`AttributesComponent` 等待遇再迁）。

## 4. 编码约定速查（AI / 人类）

### 4.1 新增实体类型

1. `EntityArchetype` 加枚举值
2. `EntityComponentAssembler::Assemble` 加组件清单
3. `ObjectFactory::CreatePrototype` 解析 category/group → 类型
4. 子类 `Init()`：`initEntityTaskHandlers()` → `ResolveDependencies()` → 业务逻辑
5. 有 `SpaceTransform` 的对象会被 `SolarSystem::addGameObject` 加入 `space_objects`

### 4.2 新增 Component

1. `GetDependencies()` 声明依赖类型
2. `InjectDependency` 优先用 `ComponentDependencyBinder`
3. 持久化：脏标记 + 节流，或走 setter 即时写
4. 头文件 **不要** include `dyn*Manager.h`（除非尚未抽象的旧代码）

### 4.3 新增 System（SolarSystem 层）

1. 新建 `include/System/XxxSystem.h` + `src/System/XxxSystem.cpp`
2. 若含 `unordered_map` 等重 STL → **`SolarSystem` 内用 `unique_ptr<XxxSystem>`**，Init 里 `make_unique`
3. 在 `SolarSystem::Update` 明确调用顺序
4. 加入 vcxproj

### 4.4 UI 交互

| 场景 | 做法 |
|------|------|
| 主菜单 / 存档 | UIF + `UIActionRegistry` → `GameApp` |
| 游戏内（旧 UI） | 创建 `Task` → `TaskMgr::addTask` |
| 禁止 | UI 里直接改 `SolarSystemMgr` 内部字段 |

### 4.5 Task 参数

**Phase 3 首批已完成**：创建用 `TaskFactory::`，读取用 `Read*` / `TryRead*`（`include/Task/TaskParams.h`）。底层仍写 `paramsPtr`，wire 格式不变。

新 taskType：在 `TaskParams.h/.cpp` 加 struct + helper，再迁移创建点与消费点；详见 [[TaskParams]]。

## 5. 编译与内存陷阱（必读）

重构 Phase 7 时多次踩坑，**后续改核心结构体务必遵守**：

### 5.1 布局变更 → Rebuild All

修改以下类型后，**必须 VS「重新生成解决方案」**，不可只增量编译：

- `GameObject` / 各 Entity 头文件成员顺序
- `SolarSystem` 成员
- Component 内联 STL 容器

否则会出现 **access violation、unordered_map 内部指针乱码**（如 `0x1110111FF0EFF17`）。

### 5.2 内联 STL → 用 `unique_ptr` 堆分配

已在项目中验证的模式：

| 位置 | 做法 |
|------|------|
| Entity `taskHandlers` | `GameObject::entityTaskHandlers` 为 `unique_ptr<EntityTaskHandlerMap>` |
| `SectorSpatialSystem` | `SolarSystem::m_sectorSpatial` 为 `unique_ptr` |
| `EntityUpdateSystem` | 同上 |

**原因**：结构体嵌入大型 `unordered_map` + 增量编译 → 成员偏移错乱。

### 5.3 `unique_ptr` 不完整类型

头文件只 forward declare、`unique_ptr` 成员时：

- 必须在 **`.cpp`** 定义析构函数（`~SolarSystem()` 等）
- 析构函数 `.cpp` 需 `#include` 完整类型

### 5.4 `/FS` 与并行编译

vcxproj 已加 `/FS` 缓解 `/MP` 下 PDB 锁冲突；Agent 侧避免与 VS 同时 MSBuild。

## 7. 改完后的验证

无自动化测试；标准路径：

1. 编译通过（布局改动后 Rebuild All）
2. 至少走一条：新建档 → 太空 → 进站/出站 或 星门跳转
3. F10 回主菜单 → 再读档，dyn 数据一致
